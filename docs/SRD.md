## 1. 引言

### 1.1 目的与范围

本文档定义 StockInvestmentTool 下一阶段改造的功能需求（FR）与非功能需求（NFR），作为研发排期、设计（HLD）、开发与验收的统一依据。

范围聚焦三件事：**能力层收敛**（地基）、**配置产品化**（策略编排器 / 通知编排器）、**体验优化**（UI 统一 / 性能）。

### 1.2 读者对象

| 角色 | 关注章节 |
|------|----------|
| 产品 | §3 需求总览、§4 功能需求、§8 边界 |
| 研发 | §4 功能需求、§6 数据需求、§7 接口需求 |
| 测试 | §4 各条验收标准、§5 非功能需求、§9 验收清单 |

### 1.3 术语表

| 术语 | 定义 |
|------|------|
| 规则 type | 方案 YAML 中 `buy_rules`/`sell_rules` 条目的类型标识，如 `support_level`、`hard_stop` |
| executor | 规则 type 对应的执行函数/类 |
| 指标表达式 | 由基础/组合/代码指标构成的算式，如 `0.95*MA20`、`MIN(MA20,MA240)` |
| 状态机 | 持仓阶段流转 `accumulating → holding → left_side → right_side → closed` |
| 触发器 | 通知系统的最小单元：`条件 × 时间/频率 × 渠道` |
| 方案（Scheme） | 一个完整策略配置，落 `schemes/*.yaml` |

## 2. 现状与问题

详见 `docs/STATUS.md` §六「问题清单」，此处仅列编号映射，作为需求来源。

| 编号 | 类别 | 一句话 |
|------|------|--------|
| A1-A7 | 架构技术债 | 两代策略引擎分叉、支撑位/状态机重复、web 单文件、数据源无抽象、指标层半接入等 |
| P1-P4 | 性能 | 个股图表逐月循环读、echarts 1MB、观察池每次实时拉取、财务史网络兜底 |
| U1-U5 | 产品/体验 | 管理模块薄弱、策略无可视化配置、通知能力弱、UI 不规整、整体不系统 |

**已确认的产品方向**（评审结论，非本 SRD 再议项）：
1. 节奏：先地基后功能；
2. 策略配置形态：可视化表单 + 后台生成 YAML（复用现有引擎与 registry）；
3. 前端路线：继续 Jinja + 原生 JS，只做统一设计系统，不引入框架。

## 3. 需求总览

### 3.1 目标与成功标准

- **G1**：策略可由用户在界面上「选择指标 → 组装规则 → 生成方案」，全程无需手写 YAML。
- **G2**：通知可由用户自定义「何时、什么条件、什么渠道」通知，配置即时生效。
- **G3**：核心页面（观察/持仓/详情）数据响应与 UI 观感达到「可用产品」水准。
- **G4**：能力层收敛后，新增一条规则/一个指标，不触碰现有策略执行逻辑即可扩展。
- **G5**：整体架构以明确设计模式组织（注册表/策略、状态、解释器、聚合器、Builder），新增功能走既定扩展点，不散落 if-else；通知按「批次」聚合发送，不各发各的。

### 3.2 需求优先级矩阵

| 优先级 | 含义 | 需求条目 |
|--------|------|----------|
| P0 | 地基，阻塞后续 | FR-1.1 统一规则派发、FR-1.3 指标×策略打通 |
| P0 | 地基 | FR-1.2 去重、FR-1.4 数据源抽象 |
| P1 | 用户核心价值 | FR-2 策略编排器、FR-3 通知编排器 |
| P1 | 体验 | FR-4 UI 统一、FR-5 性能 |
| P2 | 工程债，不阻塞价值 | （拆 web/app.py 等，本 SRD 列为 Out of Scope 候选，见 §8） |

## 4. 功能需求

> 每条需求给出编号、描述、验收标准。验收标准是可测试的检查项，测试据此写用例。

### FR-1 能力层统一（地基）

#### FR-1.1 统一规则派发

**描述**：将 v4.5 与 V6.0 两代规则 type 全部纳入统一注册表，`MultiBuyStrategy`、`TakeProfitOptimizer`、`BacktestEngineV6` 一律按 type 从注册表派发，消除「写死 type 名 + find_buy_rule("support_level")」的散落判断。

**范围 type**：`support_level`、`trend_following`、`hard_stop`、`technical_stop`、`left_side_fixed`、`right_side_trailing`（v4.5）及 `market_state_arbiter`、`logic_stop`、`price_stop`、`time_stop`（V6.0）。

**验收标准**：
- [ ] 所有上述 rule type 在统一 RuleRegistry 注册，可枚举、可查询。
- [ ] 新增一个 rule type = 注册一个 executor，不修改 `strategy/*` 已有逻辑。
- [ ] `find_buy_rule("xxx")` 这类写死 type 名的调用点全部消除。
- [ ] 现有 3 个内置方案（default_value / aggressive_growth / v6_si_wei）回测结果与改造前逐字段一致（回归通过）。
- [ ] 提供 executor 注册与派发的单元测试。

#### FR-1.2 支撑位/状态机去重

**描述**：三处重复的支撑位算法（`multi_buy.py`、`take_profit.py`、`engine_v6.py`）收敛为单一模块；持仓状态机抽为独立 `PositionStateMachine`，回测与实盘共用同一实现。

**验收标准**：
- [ ] 全库仅一处支撑位实现，三处调用点指向同一函数。
- [ ] 回测与实盘的 `year_high` 口径统一（滚动窗口与取数逻辑一致，新股/短数据期行为一致）。
- [ ] 状态机转移规则单一定义，`manager.py`/`advisor.py`/回测引擎复用。
- [ ] 支撑位与状态机各有独立单元测试覆盖。

#### FR-1.3 指标体系 × 策略打通

**描述**：`buy_rules`/`sell_rules` 的阈值与支撑源支持**引用指标表达式**（如 `threshold: "0.95*MA20"`、`support_sources: ["MA20", "MA60"]`），运行时由 `indicators/engine.py` 求值，替代写死的 `ma_60`、`low_3m` 等字符串。

**验收标准**：
- [ ] YAML 中可用指标名 + 表达式配置一条规则，回测与 advisor 能正确求值。
- [ ] 求值结果与改造前硬编码结果完全一致（回归）。
- [ ] 支持基础/组合/代码三类指标；表达式错误时给出明确报错（含指标名）。
- [ ] 老 YAML（写死字段名）保持向后兼容，无需迁移即可运行。

#### FR-1.4 数据源统一抽象 + 个股图表 DuckDB 化

**描述**：抽 `DataSource` 接口（`WarehouseSource` / `OnlineSource` 两个实现），业务层只依赖接口；`dashboard.py` 的 `stock_chart_series`、`stock_dual_view` 从「pandas 逐月循环」改为 DuckDB 单查询。

**验收标准**：
- [ ] 业务层（monitor/engine/dashboard）通过 DataSource 接口取数，无散落 if-else。
- [ ] 个股图表/详情数据读取为单次 DuckDB 查询，不再逐月 `read_parquet`。
- [ ] 观察/持仓/详情页单股数据接口耗时相较改造前显著下降（量化见 NFR-性能）。
- [ ] 数据源切换不影响上层，接口可 mock 测试。

### FR-2 策略编排器（用户核心，P1）

> 产品形态：可视化表单，保存时后台生成并校验 YAML，写入 `schemes/`，复用现有 `SchemeRegistry` 与 `AnalysisEngine`。

#### FR-2.1 指标选择器

**描述**：界面可浏览 `indicators.yaml` 定义的基础/组合/代码指标，支持搜索与定义预览，供规则参数引用。

**验收标准**：
- [ ] 列出全部指标，分组（基础/组合/代码）展示，含名称与描述。
- [ ] 支持按名称搜索。
- [ ] 每个指标可展开查看表达式/定义与说明。

#### FR-2.2 规则组装

**描述**：选择规则类型（买点/卖点/风控），以表单填写参数；阈值类参数支持选择指标并填系数（如 `0.95 × [MA20]`）。

**验收标准**：
- [ ] 覆盖 FR-1.1 全部 rule type，参数以表单（下拉/数字/开关）呈现，非裸文本。
- [ ] 阈值参数支持「系数 × 指标」的组合输入。
- [ ] 输入即时校验（数值范围、指标存在性、必填项）。

#### FR-2.3 YAML 预览与生成

**描述**：实时预览根据表单生成的方案 YAML，可复制。

**验收标准**：
- [ ] 表单变更实时刷新 YAML 预览。
- [ ] 生成的 YAML 通过 `yaml.safe_load` 与 `SchemeConfig` 校验。

#### FR-2.4 保存 / 版本 / 启停

**描述**：方案可保存、查看历史版本、启用/停用，停用方案不出现在分析/对比的可选列表中。

**验收标准**：
- [ ] 保存走原子写入（校验通过才落盘）。
- [ ] 保留历史版本，可回滚到任一历史版本。
- [ ] 启用/停用状态对 `SchemeRegistry.list()` 与前端选择生效。

#### FR-2.5 方案列表管理

**描述**：方案列表页支持新建、复制、删除、设为默认。

**验收标准**：
- [ ] 列表展示方案名/版本/适用类型/状态。
- [ ] 新建（空模板 + 从现有方案复制）两种入口。
- [ ] 删除有确认提示；内置方案删除有保护或提示。

### FR-3 通知编排器（P1）

> 产品形态：条件触发器模型，配置即时生效（免重启）。

#### FR-3.1 条件触发器模型

**描述**：用户定义触发条件，条件类型至少含：持仓操作建议（止盈/止损/加仓/调止损）、指标阈值（任意指标 上穿/下穿 某值）、价格涨跌幅。

**验收标准**：
- [ ] 支持多条件、支持 AND/OR 组合。
- [ ] 指标阈值条件可引用指标体系中的指标。
- [ ] 条件可预览最近一次是否触发（便于用户验证）。

#### FR-3.2 时间与频率配置

**描述**：定义何时检查与发送：盘中每 N 分钟、盘后定时（HH:MM）、每日一次。

**验收标准**：
- [ ] 频率/时间在界面配置，落到调度配置。
- [ ] 配置保存后即时生效（无需重启容器）。

#### FR-3.3 渠道配置 + 邮件收件人

**描述**：选择渠道（邮件/飞书/企微），邮件渠道补全收件人与 SMTP 配置。

**验收标准**：
- [ ] 渠道可切换，webhook 保存不回显明文。
- [ ] 邮件收件人可配置（补全当前为空的 `email.to`）。
- [ ] 提供「测试发送」按钮，验证配置正确。

#### FR-3.4 免重启生效

**描述**：通知规则/调度配置改动后，运行中的服务即时读取，无需重启。

**验收标准**：
- [ ] 改配置后，下一次调度按新配置执行。
- [ ] 管理页不再提示「重启后生效」。

#### FR-3.5 消息聚合（Digest）

**描述**：同一「批次」（如一次盘后周期）内，多路信号（价格阈值、资金流、持仓操作建议、盘后汇总）合并为**一条/一封**通知，按主题分节；盘中即时提醒（操作建议）保持即时发送，不与盘后 Digest 混发。

**验收标准**：
- [ ] 盘后周期内所有通知合并为一封邮件/一条 webhook 消息，按主题分节（价格提醒 / 资金流 / 持仓指令 / 汇总）。
- [ ] 盘中「操作建议」类提醒仍即时发送，不等待聚合。
- [ ] 无触发内容时，不发送空 Digest。
- [ ] 各主题内去重（同一持仓同一建议不重复出现）。

### FR-4 UI 统一与体验（P1）

#### FR-4.1 统一 base 模板与设计系统

**描述**：抽取 `base.html` 统一布局 + 一份全局 CSS + 统一组件（卡片/按钮/表单/表格/标签/Toast），16 个模板消除内联重复样式。

**验收标准**：
- [ ] 所有页面继承统一 base 模板，无各自内联 `<style>` 堆叠。
- [ ] 颜色/间距/字号/圆角以 CSS 变量统一管理。
- [ ] 移动端（≤700px）保持可用。

#### FR-4.2 导航与页面收敛

**描述**：统一顶部导航为单一组件；清理冗余/重定向路由（如 `/portfolio` → `/dashboard/warroom` 的陈旧重定向）。

**验收标准**：
- [ ] 导航由单一 `_nav.html` 组件渲染，样式一致。
- [ ] 陈旧路由与模板（`portfolio.html` 等）清理或合并。

### FR-5 性能优化（P1）

#### FR-5.1 个股图表数据接口

**描述**：个股图表/详情数据读取走 DuckDB 单查询（实现见 FR-1.4）。

**验收标准**：
- [ ] 单股 K 线/指标接口在数据仓库规模下响应达标（见 NFR-性能）。

#### FR-5.2 前端资源加载

**描述**：echarts 1MB 资源按需/拆分加载，首屏不阻塞。

**验收标准**：
- [ ] 首页首屏加载体积与耗时可测下降。
- [ ] 非图表页不加载 echarts。

## 8. 边界与不做的事（Out of Scope）

1. 不修改回测引擎的**策略算法语义**（只做派发/收敛，不改买卖止盈止损规则本身）。
2. 不引入前端框架（Vue/React），保持 Jinja + 原生 JS + ECharts。
3. 不做多账户/多租户/权限体系（保持单用户）。
4. 不做分钟级行情数据采集（盘中快照仍 10 分钟档）。
5. 拆 `web/app.py`、异步化、前端框架化，列为后续独立事项，不在本期。
