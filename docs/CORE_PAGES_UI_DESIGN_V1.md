# 核心页面 UI 设计与后台能力对齐 V1

> 适用范围：工作台、个股研究、数据中心三个核心页面。
>
> 文档目的：先确定新页面的信息架构和交互边界，再进入前端实现。本文不要求兼容当前页面布局；但所有正式展示必须以当前后台真实能力和统一领域契约为准。

## 1. 设计原则

### 1.1 页面先给结论

页面阅读顺序统一为：

```text
当前结论 → 关键数据 → 解释证据 → 可执行动作 → 技术详情
```

不把数据库对象、文件分区、日志字段直接铺成用户信息架构。

### 1.2 表格是主要信息载体

三页统一优先使用表格、状态标签、详情抽屉和 Tab。卡片只用于承载摘要，不把每个指标都做成独立大卡片。

### 1.3 可用性必须和数据状态分开

以下状态不能混用：

| 状态 | 页面表达 | 含义 |
|---|---|---|
| 正常 | 绿色“正常” | 数据或研究结果可按当前口径使用 |
| 待更新 | 橙色“待更新” | 有结果，但落后于预期日期 |
| 异常 | 红色“异常” | 最近任务失败或数据严重滞后 |
| 运行中 | 蓝色“运行中” | 任务或研究正在执行 |
| 部分可用 | 橙色“部分可用” | 核心结果可用，部分能力缺失 |
| 延期 | 灰色“延期” | 设计上存在，但当前数据契约尚未完成 |
| 不适用 | 灰色“不适用” | 该证券类型或数据项不适用，不计为缺失 |
| 暂无数据 | 灰色“暂无数据” | 没有可展示的实际数据，不能伪造为 0 |

### 1.4 AI只做总结，不做事实源

AI摘要可以将结构化结果改写成易读语言，但不能重新计算指标、覆盖 StrategyDecision、掩盖数据缺失或把延期能力写成已完成。

## 3. 统一页面框架

### 3.1 桌面端

```text
┌──────────────────────────────────────────────────────────┐
│ 左侧业务导航 │ 页面标题、描述、刷新时间、主要操作         │
├──────────────┼───────────────────────────────────────────┤
│              │ 页面级 Tab / 筛选栏                         │
│              │ 总结区                                     │
│              │ 主表格或主研究内容                         │
│              │ 解释、历史、技术详情                       │
└──────────────┴───────────────────────────────────────────┘
```

### 3.2 视觉规则

沿用数据中心现有视觉语言：浅灰背景、白色内容面板、细边框、蓝色主操作、低饱和状态色、较高信息密度。页面不使用大面积渐变、装饰性插画或只表达“看起来很智能”的无数据图形。

### 3.3 移动端

- 主表格允许横向滚动，第一列和操作列按实际宽度处理，不强行压缩文字。
- 总结区从多列改为两列或单列。
- 详情抽屉在窄屏改为全屏面板。
- 复杂筛选改为“筛选”按钮打开底部面板。
- 运行中状态仍使用短轮询，不引入 WebSocket。

## 4. 工作台页面

### 4.1 页面定位

工作台回答：

> 今天系统里有什么需要我优先关注或处理？

工作台不是所有模块的入口集合，也不直接执行真实交易。它只汇总事实、建议和入口，真实持仓变更仍进入持仓事务流程。

### 4.2 首屏结构

```text
工作台
├── 今日摘要：一句话结论 + 数据截至日期 + 总体状态
├── 今日待办：按优先级排序的事项表格
├── 持仓风险：需要处理的持仓建议
├── 观察池变化：新增、状态变化、待研究项
├── 数据与通知：数据健康、待投递、失败通知
└── 快捷操作：发现个股、分析个股、查看观察池、进入数据中心
```

### 4.3 顶部摘要

顶部只保留四个摘要值：

| 摘要 | 数据来源 | 展示方式 |
|---|---|---|
| 总体状态 | `dataset_health.overall_status` | 状态标签 + 一句话原因 |
| 当前持仓 | `GET /api/workbench/positions` | 持仓数量 |
| 观察池变化 | `GET /api/watch-pool` | 新增或待处理数量 |
| 通知状态 | `GET /api/workbench/notifications` | pending/dead 数量 |

如果市场摘要尚未接入，顶部文案应直接说明“市场状态暂未接入”，不展示空的市场卡片。

### 4.4 今日待办表格

| 列 | 内容 |
|---|---|
| 优先级 | 高、中、低 |
| 来源 | 持仓、观察池、数据中心、通知 |
| 事项 | 面向用户的简短描述 |
| 原因 | 触发该事项的实际原因 |
| 数据日期 | 事项基于哪一天的数据 |
| 下一动作 | 查看研究、查看任务、处理通知等 |
| 状态 | 待处理、已查看、已完成 |

待办排序建议为：系统异常 > 持仓风险 > 数据滞后 > 观察池变化 > 普通快捷事项。

### 4.5 后台映射

| 页面区域 | 接口 | 当前注意事项 |
|---|---|---|
| 数据状态 | `GET /api/workbench/summary` 或 `GET /api/data/status` | 当前两套状态接口并存，正式实现应选定一个 DTO，不在前端自行合并字段 |
| 观察池 | `GET /api/watch-pool` | 当前返回列表，可由前端生成摘要 |
| 持仓 | `GET /api/workbench/positions` | 当前支持持仓基础信息，不等同于完整建议接口 |
| 通知 | `GET /api/workbench/notifications` | 当前支持 counts 和最近 5 条 |
| 快捷入口 | 页面固定配置 | 只跳转，不绕过业务事务 |

### 4.6 V1 不做的内容

- 不在工作台直接买入、卖出、修改持仓。
- 不在没有后台数据时生成市场状态结论。
- 不把所有历史任务和日志放到首屏。
- 不把 AI长报告作为首页主体。

## 5. 个股研究页面

### 5.1 页面定位

个股研究回答：

> 基于哪一批数据和哪一个策略版本，这只股票当前得到什么结构化判断？

研究页面必须保留候选来源、Observation 来源、数据日期和策略版本，不能变成一个只输入股票代码、输出一段文本的分析页。

### 5.2 页面信息架构

```text
个股研究
├── 标的头部：代码、名称、研究状态、数据截至日期
├── 来源上下文：筛选运行 / 候选 / Observation / 策略版本
├── 当前结论：技术、市场、估值、基本面、综合决策
├── 入场与退出计划：数量比例、价格、止损、目标价
├── 关键证据：实际值、阈值、判断、解释、数据日期
├── K线与指标：历史走势、MA、信号点
├── 后续动作：保存观察快照、创建模拟计划、查看历史研究
└── 技术详情：DataContext、输入快照、规则轨迹、警告
```

### 5.3 结论区域

| 维度 | 后端字段 | 页面内容 |
|---|---|---|
| 技术面 | `technical_assessment` | 价格、MA20、MA60、判断、数据日期 |
| 市场面 | `market_assessment` | MarketRegime、置信度、解释、数据日期 |
| 估值面 | `valuation_assessment` | PE/PB；缺失时显示受限原因 |
| 基本面 | `fundamental_assessment` | 当前显示延期及契约原因 |
| 综合决策 | `StrategyDecision` | action、quantity_ratio、price、reason |

结论区每个维度都必须有状态，不允许只有“有值的维度”而隐藏不可用能力。

### 5.4 证据表格

| 证据类型 | 指标/规则 | 实际值 | 阈值 | 判断 | 解释 | 数据日期 |
|---|---|---:|---:|---|---|---|
| technical | 收盘价 / MA20 |  |  | 通过/未通过 |  |  |
| market | MarketRegime |  |  |  |  |  |
| valuation | PE(TTM) |  |  | 部分可用 |  |  |
| strategy_rule | 策略条件 |  |  | 触发/抑制 |  |  |

证据来自 `ResearchEvidence`。当前 `ResearchService` 生成的 `input_snapshot` 仍较简略，正式页面需要后端补充实际输入快照，至少包含标的、数据日期、相关指标值和数据上下文。

### 5.5 研究来源栏

来源栏采用一条可折叠链路：

```text
筛选运行 → 候选记录 → 个股研究 → 策略决策 → 观察/模拟
```

每个节点展示 ID、版本、日期和可点击入口。来源缺失时显示“直接发起研究”，但不能伪造候选来源。

### 5.6 研究状态

| ResearchRun 状态 | 页面表现 |
|---|---|
| `requested` | 等待执行，显示创建时间 |
| `running` | 蓝色运行中，短轮询刷新 |
| `success` | 显示完整结构化结果 |
| `partial_success` | 显示可用结果，并在顶部列出缺失能力 |
| `failed` | 显示失败原因和重新发起入口 |
| `cancelled` | 显示已取消，不使用旧结果冒充本次结果 |

### 5.7 后台缺口与建议接口

当前 `web/app.py` 没有 ResearchRun 的 Web API。正式实现前需要提供：

| 接口 | 用途 |
|---|---|
| `POST /api/research-runs` | 从 symbol、ScreenCandidate 或 Observation 创建研究 |
| `GET /api/research-runs/{run_id}` | 查询研究状态和结构化结果 |
| `GET /api/research-runs/{run_id}/evidence` | 查询证据列表 |
| `GET /api/research-runs/{run_id}/decision` | 查询 StrategyDecision |
| `GET /api/research-runs/{run_id}/report` | 查询可选报告 |
| `POST /api/research-runs/{run_id}/simulation-plan` | 从研究结果创建模拟计划 |
| `POST /api/research-runs/{run_id}/observation-snapshot` | 保存观察快照 |

在这些接口完成前，研究页可以先做静态结构和状态空态，但不应宣称正式研究流程已完成。

### 5.8 V1 不做的内容

- 不以 LLM 输出替代结构化研究结果。
- 不把基本面延期展示成“基本面正常”。
- 不在页面临时读取 Parquet、网络数据或旧接口。
- 不覆盖历史 ResearchRun，每次研究都是可查询的新运行记录。

## 6. 数据中心页面

### 6.1 页面定位

数据中心回答：

> 系统有哪些实际数据和指标，它们最新到哪里，覆盖是否足够，当前是否可信？

任务执行、日志和产物属于任务中心或详情，不作为数据中心的主分类。

### 6.2 页面信息架构

```text
数据中心
├── 总体健康摘要
├── 数据资产统计
├── 重点数据资产表格
├── 待关注数据项
├── 当前数据生产链路
└── 数据资产详情抽屉
```

现有 `data_center.html` 和 `data-module.js` 已基本具备这套结构，可将其作为视觉基线，后续重点是收敛字段、统一状态和补齐操作反馈。

### 6.3 顶部摘要

| 摘要 | 数据来源 |
|---|---|
| 数据资产总数 | `overview.counts.total` |
| 正常 | `overview.counts.healthy` |
| 待关注 | `overview.counts.attention`、`critical` |
| 运行中任务 | `overview.task_summary.running` |
| 今日完成任务 | `overview.task_summary.today_completed` |

摘要数字只作入口，不承担原因解释。原因在待关注列表和详情中展示。

### 6.4 数据资产表格

| 数据资产 | 分类 | 最新实际日期 | 覆盖 | 健康状态 | 关联任务 | 更新时间 |
|---|---|---|---|---|---|---|
| 日线行情 | 基础行情 |  |  | 正常/待更新/异常 |  |  |
| 技术指标 | 技术指标 |  |  |  |  |  |
| 研究因子 | 研究因子 |  |  |  |  |  |

覆盖字段按真实返回展示：

- 有覆盖统计：显示 `covered / expected` 和比例条；
- 没有覆盖统计：显示“暂无覆盖数据”；
- 不适用的证券类型：显示“不适用”；
- 不把缺失类型数据默认换算成 0。

### 6.5 数据资产详情抽屉

详情分为以下区域：

```text
定义与统一口径
健康情况
证券类型覆盖
来源与消费
业务影响
最近版本
当前结果预览
```

详情接口为 `GET /api/data-center/assets/{metric_key}`。Raw、Quality、checksum、版本和血缘信息默认折叠，不在首屏与业务数据混排。

### 6.6 数据生产链路

链路只展示任务级状态：

```text
采集 → 构建 → 质量 → 发布 → 派生指标
```

每一步显示：任务名称、当前状态、本次实际日期范围、最近运行时间。点击后进入任务中心，不在链路节点内展开完整日志。

### 6.7 操作规范

| 操作 | 页面文案 | 必须返回 |
|---|---|---|
| 日线同步 | 运行日线增量同步 | `run_id` 或运行记录 |
| 指标重建 | 重建技术指标 | `run_id` 或运行记录 |
| 任务查看 | 查看关联任务 | 任务详情 |
| 资产重生成 | 重新生成该数据项 | 运行记录和状态 |
| 发布/回滚 | 发布候选版本 / 回滚指定版本 | 影响范围和结果 |

高风险操作必须在确认框中说明数据集、日期范围、影响对象和是否会产生新版本。页面不得提供清空 daily 等破坏性快捷操作。

## 7. 三页之间的关系

```text
工作台
 ├─ 数据异常 → 数据中心 → 关联任务 → 运行详情
 ├─ 观察池变化 → 观察池 → 个股研究
 └─ 持仓风险 → 持仓战情室 → 研究/复盘

市场发现
 └─ ScreenCandidate → 个股研究
                         ├─ 保存 ObservationSnapshot
                         └─ 创建 SimulationPlan
```

页面跳转时尽量携带实体 ID、运行 ID、数据日期和版本，不只携带裸股票代码。

## 8. 实施顺序

### P0：统一展示契约

1. 确认工作台使用的统一数据健康 DTO，避免同时依赖两套字段口径。
2. 确认状态标签、日期、覆盖和空状态的公共渲染规则。
3. 确认数据中心当前 API 返回字段与页面字段完全对应。

### P1：数据中心视觉样板

1. 保留现有数据中心左侧导航和表格风格。
2. 收敛总览、资产列表、详情抽屉三种状态。
3. 补齐任务操作的 run_id 展示和轮询反馈。

### P2：个股研究后台契约与页面

1. 先实现 ResearchRun 查询和创建 API。
2. 再实现结论区、证据表、来源链路和数据上下文。
3. 最后接入观察快照、模拟计划和可选报告。

### P3：工作台重做

1. 以数据中心状态和现有持仓/观察池接口生成真实摘要。
2. 统一今日待办规则。
3. 市场摘要接口完成后再加入市场结论，不提前占位伪造。

## 9. 验收标准

### 工作台

- 用户能在首屏看到数据状态、持仓数量、观察池变化和通知异常。
- 有异常时能看到来源、原因和下一动作。
- 市场摘要未接入时页面明确显示未接入，而不是空白卡片。
- 工作台所有操作均为查看或跳转，不直接修改真实持仓。

### 个股研究

- 给定一个研究运行 ID，页面能显示结构化研究状态和四类评估状态。
- 每个判断能显示实际值、解释和数据日期。
- 能看到策略版本、StrategyDecision 和来源上下文。
- 基本面延期、估值降级、LLM失败等情况不会被隐藏。
- 历史研究运行不会被新的研究结果覆盖。

### 数据中心

- 能区分数据资产和任务技术对象。
- 能看到最新实际日期、覆盖、健康状态和异常原因。
- 股票、ETF、指数覆盖按类型展示；不适用不计为缺失。
- 任务操作返回可追踪的运行记录。
- 运行中任务会刷新状态，失败任务会展示可读错误原因。

## 10. 结论

三页不采用三套独立设计，而是共享同一套页面语言：

```text
工作台：总结今天要处理什么
个股研究：解释这只股票为什么得到当前判断
```
