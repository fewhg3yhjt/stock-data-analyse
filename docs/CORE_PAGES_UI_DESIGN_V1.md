# 核心页面 UI 设计与后台能力对齐 V1

> 适用范围：工作台、个股研究、数据中心三个核心页面。
>
> 文档目的：先确定新页面的信息架构和交互边界，再进入前端实现。本文不要求兼容当前页面布局；但所有正式展示必须以当前后台真实能力和统一领域契约为准。

## 1. 设计原则

### 1.1 页面先给结论

页面阅读顺序统一为：

```text
当前结论 → 关键数据 → 解释证据 → 可执行动作 → 技术详情
```

不把数据库对象、文件分区、日志字段直接铺成用户信息架构。

### 1.2 表格是主要信息载体

三页统一优先使用表格、状态标签、详情抽屉和 Tab。卡片只用于承载摘要，不把每个指标都做成独立大卡片。

### 1.3 可用性必须和数据状态分开

以下状态不能混用：

| 状态 | 页面表达 | 含义 |
|---|---|---|
| 正常 | 绿色“正常” | 数据或研究结果可按当前口径使用 |
| 待更新 | 橙色“待更新” | 有结果，但落后于预期日期 |
| 异常 | 红色“异常” | 最近任务失败或数据严重滞后 |
| 运行中 | 蓝色“运行中” | 任务或研究正在执行 |
| 部分可用 | 橙色“部分可用” | 核心结果可用，部分能力缺失 |
| 延期 | 灰色“延期” | 设计上存在，但当前数据契约尚未完成 |
| 不适用 | 灰色“不适用” | 该证券类型或数据项不适用，不计为缺失 |
| 暂无数据 | 灰色“暂无数据” | 没有可展示的实际数据，不能伪造为 0 |

### 1.4 AI只做总结，不做事实源

AI摘要可以将结构化结果改写成易读语言，但不能重新计算指标、覆盖 StrategyDecision、掩盖数据缺失或把延期能力写成已完成。

## 3. 统一页面框架

### 3.1 桌面端

```text
┌──────────────────────────────────────────────────────────┐
│ 左侧业务导航 │ 页面标题、描述、刷新时间、主要操作         │
├──────────────┼───────────────────────────────────────────┤
│              │ 页面级 Tab / 筛选栏                         │
│              │ 总结区                                     │
│              │ 主表格或主研究内容                         │
│              │ 解释、历史、技术详情                       │
└──────────────┴───────────────────────────────────────────┘
```

### 3.2 视觉规则

沿用数据中心现有视觉语言：浅灰背景、白色内容面板、细边框、蓝色主操作、低饱和状态色、较高信息密度。页面不使用大面积渐变、装饰性插画或只表达“看起来很智能”的无数据图形。

### 3.3 移动端

- 主表格允许横向滚动，第一列和操作列按实际宽度处理，不强行压缩文字。
- 总结区从多列改为两列或单列。
- 详情抽屉在窄屏改为全屏面板。
- 复杂筛选改为“筛选”按钮打开底部面板。
- 运行中状态仍使用短轮询，不引入 WebSocket。

## 4. 工作台页面

### 4.1 页面定位

工作台回答：

> 今天系统里有什么需要我优先关注或处理？

工作台不是所有模块的入口集合，也不直接执行真实交易。它只汇总事实、建议和入口，真实持仓变更仍进入持仓事务流程。

### 4.2 首屏结构

```text
工作台
├── 今日摘要：一句话结论 + 数据截至日期 + 总体状态
├── 今日待办：按优先级排序的事项表格
├── 持仓风险：需要处理的持仓建议
├── 观察池变化：新增、状态变化、待研究项
├── 数据与通知：数据健康、待投递、失败通知
└── 快捷操作：发现个股、分析个股、查看观察池、进入数据中心
```

### 4.3 顶部摘要

顶部只保留四个摘要值：

| 摘要 | 数据来源 | 展示方式 |
|---|---|---|
| 总体状态 | `dataset_health.overall_status` | 状态标签 + 一句话原因 |
| 当前持仓 | `GET /api/workbench/positions` | 持仓数量 |
| 观察池变化 | `GET /api/watch-pool` | 新增或待处理数量 |
| 通知状态 | `GET /api/workbench/notifications` | pending/dead 数量 |

如果市场摘要尚未接入，顶部文案应直接说明“市场状态暂未接入”，不展示空的市场卡片。

### 4.4 今日待办表格

| 列 | 内容 |
|---|---|
| 优先级 | 高、中、低 |
| 来源 | 持仓、观察池、数据中心、通知 |
| 事项 | 面向用户的简短描述 |
| 原因 | 触发该事项的实际原因 |
| 数据日期 | 事项基于哪一天的数据 |
| 下一动作 | 查看研究、查看任务、处理通知等 |
| 状态 | 待处理、已查看、已完成 |

待办排序建议为：系统异常 > 持仓风险 > 数据滞后 > 观察池变化 > 普通快捷事项。

### 4.5 后台映射

| 页面区域 | 接口 | 当前注意事项 |
|---|---|---|
| 数据状态 | `GET /api/workbench/summary` 或 `GET /api/data/status` | 当前两套状态接口并存，正式实现应选定一个 DTO，不在前端自行合并字段 |
| 观察池 | `GET /api/watch-pool` | 当前返回列表，可由前端生成摘要 |
| 持仓 | `GET /api/workbench/positions` | 当前支持持仓基础信息，不等同于完整建议接口 |
| 通知 | `GET /api/workbench/notifications` | 当前支持 counts 和最近 5 条 |
| 快捷入口 | 页面固定配置 | 只跳转，不绕过业务事务 |

### 4.6 V1 不做的内容

- 不在工作台直接买入、卖出、修改持仓。
- 不在没有后台数据时生成市场状态结论。
- 不把所有历史任务和日志放到首屏。
- 不把 AI长报告作为首页主体。

## 5. 个股研究页面

### 5.1 页面定位

个股研究回答：

> 基于哪一批数据和哪一个策略版本，这只股票当前得到什么结构化判断？

研究页面必须保留候选来源、Observation 来源、数据日期和策略版本，不能变成一个只输入股票代码、输出一段文本的分析页。

### 5.2 页面信息架构

```text
个股研究
├── 标的头部：代码、名称、研究状态、数据截至日期
├── 来源上下文：筛选运行 / 候选 / Observation / 策略版本
├── 当前结论：技术、市场、估值、基本面、综合决策
├── 入场与退出计划：数量比例、价格、止损、目标价
├── 关键证据：实际值、阈值、判断、解释、数据日期
├── K线与指标：历史走势、MA、信号点
├── 后续动作：保存观察快照、创建模拟计划、查看历史研究
└── 技术详情：DataContext、输入快照、规则轨迹、警告
```

### 5.3 结论区域

| 维度 | 后端字段 | 页面内容 |
|---|---|---|
| 技术面 | `technical_assessment` | 价格、MA20、MA60、判断、数据日期 |
| 市场面 | `market_assessment` | MarketRegime、置信度、解释、数据日期 |
| 估值面 | `valuation_assessment` | PE/PB；缺失时显示受限原因 |
| 基本面 | `fundamental_assessment` | 当前显示延期及契约原因 |
| 综合决策 | `StrategyDecision` | action、quantity_ratio、price、reason |

结论区每个维度都必须有状态，不允许只有“有值的维度”而隐藏不可用能力。

### 5.4 证据表格

| 证据类型 | 指标/规则 | 实际值 | 阈值 | 判断 | 解释 | 数据日期 |
|---|---|---:|---:|---|---|---|
| technical | 收盘价 / MA20 |  |  | 通过/未通过 |  |  |
| market | MarketRegime |  |  |  |  |  |
| valuation | PE(TTM) |  |  | 部分可用 |  |  |
| strategy_rule | 策略条件 |  |  | 触发/抑制 |  |  |

证据来自 `ResearchEvidence`。当前 `ResearchService` 生成的 `input_snapshot` 仍较简略，正式页面需要后端补充实际输入快照，至少包含标的、数据日期、相关指标值和数据上下文。

### 5.5 研究来源栏

来源栏采用一条可折叠链路：

```text
筛选运行 → 候选记录 → 个股研究 → 策略决策 → 观察/模拟
```

每个节点展示 ID、版本、日期和可点击入口。来源缺失时显示“直接发起研究”，但不能伪造候选来源。

### 5.6 研究状态

| ResearchRun 状态 | 页面表现 |
|---|---|
| `requested` | 等待执行，显示创建时间 |
| `running` | 蓝色运行中，短轮询刷新 |
| `success` | 显示完整结构化结果 |
| `partial_success` | 显示可用结果，并在顶部列出缺失能力 |
| `failed` | 显示失败原因和重新发起入口 |
| `cancelled` | 显示已取消，不使用旧结果冒充本次结果 |

### 5.7 后台缺口与建议接口

当前新业务蓝图已提供 ResearchRun 的基础 Web API。仍需补齐报告、观察快照和模拟计划等完整接口：

| 接口 | 用途 |
|---|---|
| `POST /api/research-runs` | 从 symbol、ScreenCandidate 或 Observation 创建研究 |
| `GET /api/research-runs/{run_id}` | 查询研究状态和结构化结果 |
| `GET /api/research-runs/{run_id}/evidence` | 查询证据列表 |
| `GET /api/research-runs/{run_id}/decision` | 查询 StrategyDecision |
| `GET /api/research-runs/{run_id}/report` | 查询可选报告 |
| `POST /api/research-runs/{run_id}/simulation-plan` | 从研究结果创建模拟计划 |
| `POST /api/research-runs/{run_id}/observation-snapshot` | 保存观察快照 |

在这些接口完成前，研究页可以先做静态结构和状态空态，但不应宣称正式研究流程已完成。

### 5.8 V1 不做的内容

- 不以 LLM 输出替代结构化研究结果。
- 不把基本面延期展示成“基本面正常”。
- 不在页面临时读取 Parquet、网络数据或旧接口。
- 不覆盖历史 ResearchRun，每次研究都是可查询的新运行记录。

## 6. 数据中心页面

### 6.1 页面定位

数据中心回答：

> 系统有哪些实际数据和指标，它们最新到哪里，覆盖是否足够，当前是否可信？

任务执行、日志和产物属于任务中心或详情，不作为数据中心的主分类。

### 6.2 页面信息架构

```text
数据中心
├── 总体健康摘要
├── 数据资产统计
├── 重点数据资产表格
├── 待关注数据项
├── 当前数据生产链路
└── 数据资产详情抽屉
```

现有 `data_center.html` 和 `data-module.js` 已基本具备这套结构，可将其作为视觉基线，后续重点是收敛字段、统一状态和补齐操作反馈。

### 6.3 顶部摘要

| 摘要 | 数据来源 |
|---|---|
| 数据资产总数 | `overview.counts.total` |
| 正常 | `overview.counts.healthy` |
| 待关注 | `overview.counts.attention`、`critical` |
| 运行中任务 | `overview.task_summary.running` |
| 今日完成任务 | `overview.task_summary.today_completed` |

摘要数字只作入口，不承担原因解释。原因在待关注列表和详情中展示。

### 6.4 数据资产表格

| 数据资产 | 分类 | 最新实际日期 | 覆盖 | 健康状态 | 关联任务 | 更新时间 |
|---|---|---|---|---|---|---|
| 日线行情 | 基础行情 |  |  | 正常/待更新/异常 |  |  |
| 技术指标 | 技术指标 |  |  |  |  |  |
| 研究因子 | 研究因子 |  |  |  |  |  |

覆盖字段按真实返回展示：

- 有覆盖统计：显示 `covered / expected` 和比例条；
- 没有覆盖统计：显示“暂无覆盖数据”；
- 不适用的证券类型：显示“不适用”；
- 不把缺失类型数据默认换算成 0。

### 6.5 数据资产详情抽屉

详情分为以下区域：

```text
定义与统一口径
健康情况
证券类型覆盖
来源与消费
业务影响
最近版本
当前结果预览
```

详情接口为 `GET /api/data-center/assets/{metric_key}`。Raw、Quality、checksum、版本和血缘信息默认折叠，不在首屏与业务数据混排。

### 6.6 数据生产链路

链路只展示任务级状态：

```text
采集 → 构建 → 质量 → 发布 → 派生指标
```

每一步显示：任务名称、当前状态、本次实际日期范围、最近运行时间。点击后进入任务中心，不在链路节点内展开完整日志。

### 6.7 操作规范

| 操作 | 页面文案 | 必须返回 |
|---|---|---|
| 日线同步 | 运行日线增量同步 | `run_id` 或运行记录 |
| 指标重建 | 重建技术指标 | `run_id` 或运行记录 |
| 任务查看 | 查看关联任务 | 任务详情 |
| 资产重生成 | 重新生成该数据项 | 运行记录和状态 |
| 发布/回滚 | 发布候选版本 / 回滚指定版本 | 影响范围和结果 |

高风险操作必须在确认框中说明数据集、日期范围、影响对象和是否会产生新版本。页面不得提供清空 daily 等破坏性快捷操作。

## 7. 三页之间的关系

```text
工作台
 ├─ 数据异常 → 数据中心 → 关联任务 → 运行详情
 ├─ 观察池变化 → 观察池 → 个股研究
 └─ 持仓风险 → 持仓 → 研究/复盘

市场发现
 └─ ScreenCandidate → 个股研究
                         ├─ 保存 ObservationSnapshot
                         └─ 创建 SimulationPlan
```

页面跳转时尽量携带实体 ID、运行 ID、数据日期和版本，不只携带裸股票代码。

## 8. 实施顺序

### P0：统一展示契约

1. 确认工作台使用的统一数据健康 DTO，避免同时依赖两套字段口径。
2. 确认状态标签、日期、覆盖和空状态的公共渲染规则。
3. 确认数据中心当前 API 返回字段与页面字段完全对应。

### P1：数据中心视觉样板

1. 保留现有数据中心左侧导航和表格风格。
2. 收敛总览、资产列表、详情抽屉三种状态。
3. 补齐任务操作的 run_id 展示和轮询反馈。

### P2：个股研究后台契约与页面

1. 先实现 ResearchRun 查询和创建 API。
2. 再实现结论区、证据表、来源链路和数据上下文。
3. 最后接入观察快照、模拟计划和可选报告。

### P3：工作台重做

1. 以数据中心状态和现有持仓/观察池接口生成真实摘要。
2. 统一今日待办规则。
3. 市场摘要接口完成后再加入市场结论，不提前占位伪造。

## 9. 验收标准

### 工作台

- 用户能在首屏看到数据状态、持仓数量、观察池变化和通知异常。
- 有异常时能看到来源、原因和下一动作。
- 市场摘要未接入时页面明确显示未接入，而不是空白卡片。
- 工作台所有操作均为查看或跳转，不直接修改真实持仓。

### 个股研究

- 给定一个研究运行 ID，页面能显示结构化研究状态和四类评估状态。
- 每个判断能显示实际值、解释和数据日期。
- 能看到策略版本、StrategyDecision 和来源上下文。
- 基本面延期、估值降级、LLM失败等情况不会被隐藏。
- 历史研究运行不会被新的研究结果覆盖。

### 数据中心

- 能区分数据资产和任务技术对象。
- 能看到最新实际日期、覆盖、健康状态和异常原因。
- 股票、ETF、指数覆盖按类型展示；不适用不计为缺失。
- 任务操作返回可追踪的运行记录。
- 运行中任务会刷新状态，失败任务会展示可读错误原因。

## 10. 结论

三页不采用三套独立设计，而是共享同一套页面语言：

```text
工作台：总结今天要处理什么
个股研究：解释这只股票为什么得到当前判断
数据中心：说明这些判断依赖的数据是否可信
```

第一轮前端实现应优先建立数据中心的公共表格、状态和抽屉规范；个股研究必须先补齐 Web API；工作台则基于真实接口做总结，不为填满页面而增加尚未实现的市场和 AI 能力。

## 11. 前端优先页面设计

本章针对不需要新增后台接口的页面。实现时允许在前端增加页面级 Adapter，将现有接口字段转换为统一展示模型；不允许在前端推测后台没有返回的事实，也不允许用空值、0 或固定文案伪造业务结果。

### 11.1 市场发现

#### 页面目标

市场发现回答：

> 在指定数据日期和筛选条件下，哪些股票满足条件，为什么满足，下一步应该做什么？

#### 页面结构

```text
市场发现
├── 页面摘要：数据来源、数据日期、当前运行状态
├── 筛选方案：基础条件、高级条件、保存/加载模板
├── 条件摘要：已启用条件和条件数量
├── 运行结果：命中数量、当前页、排序方式
├── 候选表格：股票、指标、命中条件、数据日期、动作
└── 候选详情：K线、指标、命中解释、观察/研究/模拟入口
```

#### 候选表格

| 列 | 内容 |
|---|---|
| 股票 | 代码、名称、市场和行业 |
| 最新价 | 当前筛选日期的价格 |
| 涨跌表现 | 当日或统计周期涨跌幅 |
| 成交与估值 | 成交额、换手率、PE、PB，缺失显示“暂无” |
| 命中条件 | 条件名称或命中标签 |
| 数据日期 | 本次结果的实际数据日期 |
| 下一步 | 展开K线、分析、加入观察 |

#### 现有接口映射

| 页面能力 | 当前接口 | 前端策略 |
|---|---|---|
| 筛选选项 | `GET /api/market-discovery/options` | 读取行业等选项 |
| 执行筛选 | `POST /api/market-discovery/stocks` | 负责加载、分页和排序 |
| K线详情 | `GET /api/market-discovery/series` | 在表格行下方或右侧面板展开 |
| 加入观察 | 当前页面的 `/watchlist` 写入入口 | 保留候选代码、名称和原因摘要 |
| 个股分析 | `/analyze` 或既有分析入口 | 跳转时携带代码、名称和候选上下文 |

#### 交互要求

- 筛选执行中显示运行状态，按钮不可重复提交。
- 空列表只表示执行成功但没有命中，不与查询失败混用。
- 数据滞后、字段缺失和接口失败要分别展示。
- 点击表头排序时保留筛选条件和页码语义。
- K线详情显示数据范围，不把返回的空数组解释为“没有行情”。
- “加入观察”后保留来源原因，不能只写入裸股票代码。

#### 不做的内容

- 不在前端重新计算筛选规则。
- 不把未发布指标作为筛选结果补充展示。
- 不增加后台没有返回的评分、排名或市场状态。

#### 验收标准

- 用户可以填写条件、执行筛选、查看总命中数和分页结果。
- 每个候选可以展开K线，并能看到数据日期。
- 无命中、缺字段、接口失败分别有明确文案。
- 候选可以进入分析或观察流程。

### 11.2 观察池

#### 页面目标

观察池回答：

> 哪些对象正在跟踪，它们从哪里来，当前处于什么状态，下一步是什么？

#### 页面结构

```text
观察池
├── 总结摘要：观察对象数、待模拟、待建仓、已持仓
├── 数据健康提示：日线实际日期和状态
├── 状态筛选：全部、候选、待模拟、待建仓、已持仓
├── 观察对象表格
└── 单项详情：来源、观察数据、模拟、持仓和下一动作
```

#### 观察对象表格

| 列 | 内容 |
|---|---|
| 标的 | 代码、名称 |
| 来源 | 自选、策略、筛选候选等，支持多个来源 |
| 加入时间 | 原始观察或关注时间 |
| 当前状态 | 候选、待模拟、待建仓、已持仓 |
| 最新行情 | 价格、市场状态或可用的观察值 |
| 风险提示 | 风险灯、数据缺失或暂停原因 |
| 下一动作 | 进入分析、运行模拟、查看持仓 |

#### 现有接口映射

| 页面能力 | 当前接口 | 前端策略 |
|---|---|---|
| 观察池数据 | `GET /api/watch-pool` | 以返回的 merged item 为页面数据源 |
| 强制刷新 | `/api/watch-pool?refresh=1` | 明确标注正在重新计算，避免误认为普通刷新 |
| 数据健康 | 接口中的 `data_health` | 放在页面摘要和异常提示中 |
| 模拟 | 既有 `/api/simulation` 入口 | 保留当前对象上下文 |
| 关注关系 | `/watchlist` 相关既有接口 | 在详情中区分关注和观察周期 |

#### 交互要求

- 来源必须作为重要字段展示，不能只展示股票代码。
- 已存在于多个关系中的股票合并为一行，但来源列表不能丢失。
- 强制刷新期间显示加载状态，不允许重复触发。
- 数据严重滞后时可以继续查看，但模拟或建仓入口要显示数据风险提示。
- 详情优先使用右侧抽屉，避免用户离开观察池后丢失上下文。

#### 不做的内容

- 不在前端创建新的 Observation 实体。
- 不把观察池直接当作真实持仓。
- 不根据前端当前列表推断历史来源。

#### 验收标准

- 用户可以区分来源、当前状态和下一动作。
- 同一标的多来源时只显示一行，且来源完整。
- 数据异常时页面能明确说明原因并链接数据中心。
- 可从观察对象进入模拟或现有分析流程。

### 11.3 持仓

#### 页面目标

持仓页面回答：

> 当前持有什么，风险在哪里，建议是什么，哪些信息需要进一步确认？

#### 页面结构

```text
持仓
├── 账户与持仓摘要
├── 风险总览：正常、防守、危机
├── 当前持仓表格
├── 操作建议表格
├── 最近成交与流水
└── 持仓详情：行情、成本、止损、研究和交易入口
```

#### 持仓表格

| 列 | 内容 |
|---|---|
| 标的 | 代码、名称 |
| 持仓数量 | 总股数和可用数量 |
| 成本 | 成本价、成本金额 |
| 当前行情 | 当前价、浮动盈亏 |
| 仓位 | 当前占比 |
| 风险状态 | 正常、防守、危机 |
| 建议 | 持有、加仓、减仓、清仓或调止损 |
| 操作 | 查看详情、进入既有交易流程 |

#### 现有接口映射

当前页面由 `/dashboard/warroom` 提供服务端聚合数据，相关数据来自 `DashboardService.war_room()`、持仓管理和看板服务。前端改版应优先消费页面已有数据，不直接读取数据库或重新调用底层行情源。既有个股图表接口可用于详情区域：

```text
GET/POST /api/chart/stock
```

#### 交互要求

- 风险和建议放在表格前部，行情图表放入详情区域。
- 操作建议必须显示来源或触发原因，不能只显示动作名称。
- 真实买卖、持仓修改仍进入原有事务页面或接口。
- 没有持仓时显示账户空状态和进入观察池/市场发现入口。
- 当前价格不可用时显示“暂无实时价格”，不按 0 计算盈亏。

#### 不做的内容

- 不在前端直接修改持仓数量、成本或现金。
- 不根据颜色自行判断买卖信号。
- 不把模拟仓位和真实持仓混在同一张表中。

#### 验收标准

- 首屏能看到持仓数量、风险状态和建议。
- 用户可以打开单个持仓的详情和相关图表。
- 真实交易入口仍遵守原有流程。
- 行情缺失、建议缺失和持仓为空有不同状态。

### 11.4 复盘

#### 页面目标

复盘回答：

> 已经发生的交易和持仓周期结果如何，哪些决策有效，哪里存在执行偏差？

#### 页面结构

```text
复盘
├── 复盘摘要：收益、胜率、盈亏比、回撤
├── 结果结论：最值得关注的变化
├── 持仓周期/交易记录表格
├── 执行偏差表格
├── 复盘证据和备注
└── 导出复盘结果
```

#### 统计表格

| 指标 | 当前值 | 参考值 | 结论 |
|---|---:|---:|---|
| 总收益率 |  |  |  |
| 胜率 |  |  |  |
| 盈亏比 |  |  |  |
| 最大回撤 |  |  |  |
| 持仓周期 |  |  |  |
| 执行偏差 |  |  |  |

#### 现有接口映射

当前 `/dashboard/review` 由 `DashboardService.review_ledger()` 服务端聚合数据，页面还提供：

```text
GET /dashboard/review/export
```

前端只负责把已有统计、记录和诊断字段整理为总结区和表格，不在浏览器中重新计算收益、FIFO 或交易周期。

#### 交互要求

- 首屏先显示总结和关键结论，再展示明细。
- 明细表支持按时间、标的和结果筛选。
- 统计缺失时显示“暂无复盘数据”，不显示一组默认 0。
- 导出操作显示当前复盘范围和生成状态。
- 交易记录、持仓周期和策略模拟结果必须明确标注类型。

#### 不做的内容

- 不在前端复制收益计算逻辑。
- 不把回测结果当作真实交易结果。
- 不用图表替代交易记录和结论说明。

#### 验收标准

- 用户能先看到收益和风险总结，再进入交易明细。
- 真实交易、持仓周期和模拟结果有清晰区分。
- 导出入口可用，空数据和失败状态可读。

### 11.5 通知中心

#### 页面目标

通知中心回答：

> 哪些是业务上的提醒，哪些是系统告警，哪些消息还没有成功送达？

#### 页面结构

```text
通知中心
├── 摘要：待投递、已发送、失败/死信
├── Tab：业务通知
├── Tab：系统告警
├── Tab：投递状态
└── 通知详情：事件、对象、通道、重试记录
```

#### 投递表格

| 列 | 内容 |
|---|---|
| 时间 | 事件或投递时间 |
| 类型 | 持仓建议、价格、资金流、系统告警等 |
| 标题 | 面向用户的通知内容 |
| 关联对象 | 股票、任务、数据集或系统 |
| 通道 | 邮件、Webhook 等 |
| 状态 | pending、retrying、sent、failed、dead |
| 操作 | 重试、查看详情 |

#### 现有接口映射

| 页面能力 | 当前接口 |
|---|---|
| 通知规则 | `GET/POST /api/notify/rules` |
| 通知配置 | `GET /api/notify/config` |
| 投递列表 | `GET /api/notify/outbox` |
| 单条重试 | `POST /api/notify/outbox/{item_id}/retry` |
| 重试死信 | `POST /api/notify/outbox/retry-dead` |
| 生成系统告警 | `POST /api/system/alerts` |
| 测试通道 | `POST /api/notify/test` |

当前 `notify_composer.html` 已覆盖规则、配置、测试和 outbox 操作。前端改造应将这些区域拆成 Tab 或主表格 + 抽屉，而不是继续堆叠成长表单。

#### 交互要求

- 业务通知、系统告警、投递状态必须视觉分组。
- `dead` 和 `failed` 要突出显示，并给出重试入口。
- 重试后显示请求结果，并刷新当前列表。
- 生成系统告警是有副作用操作，需要明确确认或操作说明。
- 测试通道和真实投递状态分开显示。

#### 不做的内容

- 不把系统告警伪装成持仓业务通知。
- 不在前端修改通知事件状态而不调用后端。
- 不把发送成功等同于用户已经阅读。

#### 验收标准

- 三类通知状态可以快速区分。
- 用户可以筛选 pending、failed、dead，并执行重试。
- 通知详情能看到关联对象和投递通道。
- 失败和死信不会被空列表或普通成功提示掩盖。

### 11.6 系统设置

#### 页面目标

系统设置回答：

> 当前系统使用什么策略、通知和运行配置，哪些配置会影响后续任务？

#### 页面结构

```text
系统设置
├── 策略与方案
├── 初筛和通知规则
├── 通知通道
├── 账户与登录
├── 数据与运行开关
└── 危险操作
```

#### 页面组织

| 区域 | 展示重点 | 操作方式 |
|---|---|---|
| 策略与方案 | 当前方案、版本、启用状态 | 进入策略配置或方案页面 |
| 初筛规则 | 当前规则和启用状态 | 使用现有设置提交入口 |
| 通知配置 | Webhook、邮箱和通道状态 | 测试前先显示目标通道 |
| 账户与登录 | 用户名、登录启用状态 | 单独的账户表单 |
| 数据运行 | 调度、快照、日线同步状态 | 跳转数据中心和诊断 |
| 危险操作 | 重置、删除或清理 | 独立危险区，显示影响范围 |

#### 现有接口映射

当前设置相关入口包括：

```text
POST /settings/scheme
POST /settings/screen-rules
POST /settings/notify
POST /settings/account
POST /settings/reset
```

系统诊断使用 `GET /api/health/details`，方案、指标和通知还有各自的专用 API。页面可以重新组织视觉层次，但不要把不同领域配置合并成一个前端 JSON 提交对象。

#### 交互要求

- 保存成功、保存失败和配置未变化使用不同反馈。
- 需要生效的配置显示影响范围和生效时机。
- 危险操作默认折叠，确认框说明会影响什么、能否恢复。
- 账户、通知密钥和密码输入不得回显敏感值。
- 运行状态信息采用只读展示，具体任务操作进入数据中心或任务中心。

#### 不做的内容

- 不在系统设置中复制任务中心的完整任务配置编辑器。
- 不在前端保存密码、密钥或 Webhook 明文到 localStorage。
- 不提供绕过后端确认的重置和清理操作。

#### 验收标准

- 用户能快速找到策略、通知、账户和运行配置。
- 每个保存动作有明确结果反馈。
- 危险操作单独隔离并说明影响范围。
- 页面不会把敏感配置直接展示或持久化到浏览器。

### 11.7 页面共用组件

前端优先改造的页面统一复用数据中心已经验证过的组件语言：

| 组件 | 统一行为 |
|---|---|
| 页面头部 | 标题、说明、最近刷新时间、主要操作 |
| 摘要区 | 少量关键数字 + 当前状态，不放全部字段 |
| 表格 | 结果主体，支持横向滚动、空状态和行操作 |
| 状态标签 | 使用统一状态颜色和中文文案 |
| 详情抽屉 | 展示来源、解释、历史和技术信息 |
| 操作反馈 | 页面内显示提交中、成功、失败，不使用 `alert` 作为主要反馈 |
| 数据日期 | 统一使用“实际数据日期”，不把请求日期写成数据已更新 |
| 空状态 | 区分暂无数据、无命中、未配置、未启用和读取失败 |
| 风险确认 | 所有副作用操作说明对象、范围和影响 |

### 11.8 前端实施顺序

```text
市场发现
→ 观察池
→ 持仓
→ 复盘
→ 通知中心
→ 系统设置
```

原因是这条顺序对应现有业务链路，并且前 3 个页面的数据接口相对稳定。每个页面单独完成以下步骤：

1. 保留现有路由和接口。
2. 新增页面级 Adapter，隔离接口字段。
3. 使用数据中心的布局、表格、状态和抽屉样式。
4. 先覆盖加载、空数据、失败和移动端状态。
5. 运行页面契约测试和 JavaScript 语法检查。
6. 重启生产 Web 容器后进行页面冒烟验证。

个股研究页面已在 ResearchRun 基础 Web API 接入后实现第一版正式详情页；报告、观察快照、模拟计划和更完整的历史轮询仍按后台能力完成情况逐步接入。

- 当前 `workbench.html/workbench.js` 已完成视觉改版，但仍消费旧的 `/api/workbench/*` 和 `/api/watch-pool` 聚合接口，属于页面改版，不属于新业务 API 主链路切换。
- 新业务正式 API 的筛选、研究和模拟创建接口均返回 `202 + run_id + status_url`，页面接入时必须采用短轮询，不得等待 HTTP 请求直接返回计算结果。
- 个股研究详情页已通过 `business-runs/{run_id}` 轮询 requested/running/terminal 状态；完成后再读取 ResearchRun 结果。

## 12. 全量页面设计基线

本章把仓库中现有模板全部纳入统一审视范围。它的作用是确定每个页面的产品职责和最终落位，不代表所有页面都要在同一批次重写。

### 12.1 全局导航与页面归类

一级导航只表达业务领域，不直接暴露所有技术页面：

```text
工作台
市场
观察池
持仓
研究
复盘
系统
```

页面归类如下：

| 一级领域 | 主页面 | 二级页面/辅助页面 |
|---|---|---|
| 工作台 | `/workbench` | `/` 作为工作台入口；带股票参数时转入 `/analyze` |
| 市场 | `/market` | `/market-discovery`、`/compare` |
| 观察池 | `/watch-pool` | `/dashboard/observe`、`/watchlist`、`/simulation` |
| 持仓 | `/dashboard/warroom` | `/portfolio`、`/portfolio/add`、`/portfolio/{id}`、`/position_detail` |
| 研究 | `/research` | `/analyze`、`/indicator-center`、`/strategy-composer`、`/strategy`、`/operation-points` |
| 复盘 | `/dashboard/review` | `/morning-report`、`/operation-log`、`/quicklog` |
| 系统 | `/data-center` | `/data-center/assets`、`/data-center/tasks`、`/notify-center`、`/diagnostics`、`/settings`、`/system` |

旧入口不要求立即删除，但必须满足：

- 用户导航只出现一个主入口；
- 旧页面明确显示自己属于哪个主模块；
- 页面之间不产生重复数据口径；
- 旧入口只负责跳转或提供尚未归并的具体操作；
- 不为了兼容旧地址而保留第二套长期业务流程。

### 12.2 市场概览 `/market`

#### 页面目标

回答：

> 今天市场整体处于什么状态，指数、板块和关注标的有什么共同变化？

#### 页面结构

```text
市场概览
├── 日期与市场状态摘要
├── 指数表现表格
├── 板块表现表格
├── 资金与成交摘要
├── 指数/板块走势图
└── 进入个股发现和个股分析
```

#### 主要表格

| 表格 | 字段 |
|---|---|
| 指数 | 指数名称、最新价、涨跌幅、成交额、数据日期 |
| 板块 | 板块名称、涨跌幅、强弱排名、成交额、数据日期 |
| 市场摘要 | 上涨数、下跌数、涨停/跌停等实际可用字段 |

#### 接口和边界

当前使用 `/market` 页面以及 `/market/index_kline`、`/market/board_kline`、`/market/stock_chart` 等接口。前端只负责组合已有行情和图表数据；没有统一市场状态字段时显示“市场状态暂无统一判断”，不自行拼出强多、弱空等结论。

#### 视觉重点

这是“观察市场”的页面，图表可以比数据中心更多，但每张图都必须有日期、来源和加载状态。核心排序仍以表格为主，图表是解释工具，不是装饰大屏。

### 12.3 个股分析 `/analyze`

#### 页面目标

回答：

> 这只股票的行情、指标和已有分析结果是什么，哪些参数影响了结果？

#### 页面结构

```text
个股分析
├── 标的搜索和分析参数
├── 标的概览：代码、名称、数据日期
├── 行情图表：K线、成交量、指标线
├── 分析结果：技术、估值、风险、建议
├── 多方案对比入口
└── 进入研究、观察和模拟
```

#### 主要字段

| 区域 | 字段 |
|---|---|
| 参数 | 标的、方案、日期范围、是否生成报告 |
| 行情 | 开高低收、成交量、均线、数据日期 |
| 结果 | 类型判断、评分、风险提示、建议 |
| 追溯 | 方案名称、方案版本、数据源、分析时间 |

#### 接口和边界

当前 `/analyze` 仍是既有分析表单和结果入口，适合先按数据中心样式重排为“参数区 + 结果表格 + 详情”。不要把它与正式 `ResearchRun` 混为一体；正式研究结果仍等待研究 API。

### 12.4 多方案对比 `/compare`

#### 页面目标

回答：

> 同一标的或同一批输入，在不同策略方案下的结果有什么差异？

#### 页面结构

```text
对比分析
├── 对比对象和方案选择
├── 结果总览表
├── 关键指标差异
├── 建议差异
└── 进入单方案分析
```

| 表格字段 | 内容 |
|---|---|
| 方案 | 名称、版本、状态 |
| 结果 | 评分、分类、建议 |
| 差异 | 与基准方案相比的变化 |
| 来源 | 数据日期、分析时间 |

对比页不重新计算方案逻辑，只展示服务端返回的对比结果；缺失值用“暂无”而不是 0。

### 12.5 观察与自选页面

#### `/watch-pool` 主页面

使用第 11.2 节的观察池设计，作为观察业务主入口。

#### `/dashboard/observe` 观察看板

定位为观察池的增强视图，适合展示市场状态、支撑位、操作指令和候选来源。不要与 `/watch-pool` 维护两套观察数据；主入口负责对象管理，观察看板负责分析视图。

#### `/watchlist` 自选管理

定位为用户关注关系管理：

```text
自选列表 → 添加/删除 → 设置加入时间 → 发起模拟或分析
```

表格字段为代码、名称、加入时间、来源、备注、下一动作。自选不是 Observation，也不是持仓；页面需要在标题或说明中明确这一点。

#### `/simulation` 模拟

作为观察池和策略实验之间的模拟执行页面：

```text
模拟计划 → 模拟运行 → 成交/事件 → 结果摘要 → 进入复盘
```

表格优先展示模拟计划、标的集合、策略版本、资金、区间、状态和结果。真实持仓操作不在模拟页执行。

### 12.6 持仓页面

#### `/dashboard/warroom` 持仓

使用第 11.3 节设计，作为持仓主入口，面向“今天应该处理哪些持仓风险”。页面对用户统一称为“持仓”。

#### `/portfolio` 持仓管理

定位为账户和持仓事务管理页，重点展示：

| 区域 | 内容 |
|---|---|
| 账户 | 账户名称、现金、总资产、更新时间 |
| 持仓 | 标的、数量、成本、当前价、盈亏 |
| 事务 | 添加、编辑、成交、平仓 |
| 导入导出 | 文件范围、成功/失败结果 |

持仓页负责判断和建议，持仓管理负责事实和事务，两者不能在页面层混为一个“买卖面板”。

#### `/portfolio/add`、`/portfolio/{id}`、`/position_detail`

这些页面统一作为持仓详情和操作面板：

- 新增页：输入标的和初始持仓信息；
- 详情页：持仓成本、成交、策略和建议；
- 操作页：单次成交、平仓、编辑和删除；
- 所有有副作用的操作显示影响范围、确认和结果。

### 12.7 研究工具页面

#### `/research` 研究中心

定位为研究工作区导航，不直接堆叠研究结果。首屏展示研究流程和最近使用入口：

```text
个股分析 → 指标中心 → 策略编排 → 策略实验 → 结果进入观察/模拟
```

#### `/indicator-center` 指标中心

页面结构：

```text
指标目录 → 指标定义 → 表达式编辑 → 样本预览 → 启用状态
```

表格字段为指标名称、类型、表达式、说明、状态、更新时间、操作。现有 `/api/indicators`、`save`、`toggle`、`delete`、`preview` 已能支撑前端重排。删除和停用必须区分，内置指标不能提供删除按钮。

#### `/strategy-composer` 策略编排

页面结构：

```text
策略信息 → 入场规则 → 退出规则 → 风控和仓位 → 校验 → 发布
```

右侧或底部固定显示校验结果和影响范围。条件配置使用结构化控件，只有在用户进入高级模式时才展示 YAML/表达式原文。

现有 `/api/rules/schema`、`/api/schemes/compose`、`parse`、`validate`、`publish`、`impact` 等接口作为数据源。保存草稿、校验通过、发布成功必须是三个不同状态。

#### `/strategy` 策略实验

页面结构：

```text
实验参数 → 扫描结果 → 回测结果 → 收益曲线 → 交易明细
```

表格优先展示策略、数据区间、标的数、命中数、运行状态、收益率、最大回撤和运行时间。扫描、回测和图表请求状态要分开显示，不能用一个“运行完成”覆盖所有阶段。

#### `/operation-points` 操作点位

定位为单标的操作研究工具：

```text
输入标的 → 点位分析 → 支撑/止损/目标 → RR判断 → 历史回测
```

首屏显示结论表格，不先显示全部参数。参数、计算结果、诊断信息和回测结果分区，明确“参数未保存为策略版本”的当前边界。

### 12.8 复盘与记录页面

#### `/dashboard/review` 复盘主页面

使用第 11.4 节设计，作为收益和执行效果的主入口。

#### `/morning-report` 晨报

定位为只读摘要页面：

```text
市场摘要 → 持仓摘要 → 观察池变化 → 通知和风险 → 数据日期
```

内容优先使用短段落和总结表格，不把晨报做成完整交易工作台。生成失败时显示失败原因和最近成功时间。

#### `/operation-log`、`/quicklog`

统一定位为操作记录：

- `/operation-log` 展示结构化操作、时间、标的、动作、原因和结果；
- `/quicklog` 用于快速录入或查看简短记录；
- 两者共享记录语义，不要出现一边记录“建议”、另一边记录“成交”但没有类型标签的情况。

### 12.9 系统页面

#### 数据中心与任务中心

使用第 4 节和第 6 节设计，作为系统页面视觉基准。

#### `/notify-center`

使用第 11.5 节设计。当前模板名为 `notify_composer.html`，页面对用户应称为“通知中心”，编辑规则只是其中一个 Tab，不应成为整个页面名称。

#### `/diagnostics`

定位为只读运行诊断页，回答：

> 应用、调度、数据、通知和登录安全是否正常？

页面结构：

```text
诊断摘要 → 分类状态表 → 最近任务 → 通知队列 → 进入处理页面
```

使用 `GET /api/health/details`。诊断页不直接修改配置，异常项提供进入数据中心、任务中心或通知中心的入口。

#### `/settings` 与 `/system`

`/system` 是系统模块入口或概览页，`/settings` 是实际设置页。统一使用第 11.6 节设计，不再让用户在两个页面之间猜测“配置到底在哪”。

建议：

- `/system` 展示系统概览和各系统工具入口；
- `/settings` 承担配置读写；
- 数据任务配置进入任务中心；
- 数据健康进入数据中心；
- 通知规则和投递进入通知中心；
- 危险操作只放在设置页底部。

### 12.10 辅助和认证页面

#### `/login`

登录页保持极简：产品名称、用户名、密码、登录结果和安全提示。错误信息就地显示，不暴露账户是否存在等内部细节。

#### `base.html`、`_nav.html`

它们不是用户页面，但属于全局 UI 基础设施：

- `base.html` 负责字体、公共 CSS、viewport、toast 容器；
- `_nav.html` 负责传统业务页面的一级和二级导航；
- 数据中心/任务中心/工作台当前有独立工作区壳层，后续应统一导航数据但保留各页面适合的布局。

### 12.11 全量页面实施分组

为了后续统一审视，将页面分为五组：

| 分组 | 页面 | 统一模板 |
|---|---|---|
| A 系统工作区 | 工作台、数据中心、任务中心、诊断、通知 | 状态摘要 + 表格 + 详情抽屉 |
| B 市场工作区 | 市场概览、市场发现、对比 | 数据日期 + 筛选/行情表格 + 图表详情 |
| C 投资工作区 | 观察池、自选、模拟、持仓、持仓详情 | 对象状态 + 风险/建议 + 事务入口 |
| D 研究工作区 | 研究中心、个股分析、指标、策略编排、策略实验、操作点位 | 参数/定义 + 结构化结果 + 版本/来源 |
| E 复盘工作区 | 复盘、晨报、操作日志、快速记录 | 总结结论 + 历史记录 + 导出 |

建议实现顺序调整为：

```text
A 组收口
→ B 组市场发现和市场概览
→ C 组观察池和持仓
→ E 组复盘与记录
→ D 组研究工具
```

其中个股研究正式页仍需等待后台 ResearchRun API；个股分析、指标、策略编排、策略实验和操作点位可以先按现有接口独立改版。

### 12.12 全量审视清单

统一审视时逐页检查：

| 检查项 | 判断标准 |
|---|---|
| 页面职责 | 一页只回答一类主要问题 |
| 首屏结论 | 用户无需先读完整表格才能知道当前状态 |
| 表格字段 | 字段服务于判断，不直接暴露内部表结构 |
| 状态语义 | 正常、滞后、异常、运行中、延期、暂无数据不混用 |
| 日期口径 | 明确实际数据日期、请求日期和更新时间 |
| 来源链路 | 候选、观察、研究、模拟、持仓之间能追溯 |
| 副作用操作 | 有影响范围、确认和结果反馈 |
| 空状态 | 无数据、无命中、未配置、未启用和读取失败有区分 |
| 页面关系 | 跳转携带实体上下文，不只携带裸代码 |
| 移动端 | 表格可读，详情可操作，复杂筛选可收起 |
| 后台依赖 | 当前没有的能力明确标记，不在前端伪造 |

### 13.5 复盘、通知和设置


## 16. 操作分级与组件规格

### 16.1 操作分级

| 级别 | 示例 | 页面规则 |
|---|---|---|
| 查看 | 查看详情、查看K线、查看日志 | 直接打开抽屉或详情区域 |

| 高风险操作 | 删除、回滚、重置、清理 | 独立危险区，明确不可逆影响 |

### 16.2 共用组件规格

| 组件 | 规格基线 |
|---|---|
| 页面壳层 | 数据中心同款深色侧栏；桌面侧栏约 218px，移动端变为横向导航 |

## 20. 全量改造阶段整改清单

本清单记录全量前端迁移过程中的已知问题。页面改造可以先完成视觉和交互框架，但以下项目需要在后续统一整改或验收时逐项确认。

| 编号 | 问题 | 当前表现 | 影响 | 处理建议 |
|---|---|---|---|---|
| UI-01 | 旧页面与新页面脚本仍有差异 | 新页面使用公共状态/反馈资源，部分旧页面仍有内联脚本 | 维护成本和状态文案可能继续分叉 | 逐页将内联脚本迁移到页面级 JS，再删除重复常量 |
| UI-02 | 原生确认框仍存在 | 删除、回滚、平仓、输入价格等操作仍使用 `confirm/prompt` | 移动端体验不一致，无法展示完整影响范围 | 建立统一确认/输入面板，保留同步业务语义 |
| UI-03 | API 响应信封双轨 | 旧接口直接返回 `status + 字段`，新业务接口返回 `data + request_id` | 页面 Adapter 需要判断两种结构 | 后续统一请求适配器，明确错误码、数据和请求 ID |
| UI-04 | 数据健康接口双轨 | 工作台使用 `/api/data/status`，数据中心使用 `/api/data-center/overview` | 同一数据项存在跨页面口径不一致风险 | 后端确定唯一健康事实，前端只做字段映射 |
| UI-05 | 任务执行追踪不完整 | 部分执行接口返回“已提交”但没有本次 `run_id` | 用户无法精确跟踪当前点击对应的运行 | 执行接口返回运行编号，前端按运行编号轮询 |
| UI-06 | 资产详情历史实现残留 | 数据总览、数据资产管理曾各自维护详情渲染逻辑 | 字段和空状态容易出现差异 | 保留单一资产详情渲染器，管理操作作为插件注入 |
| UI-07 | 任务产物接口命名不一致 | 日志和产物分别挂在不同 API 前缀 | 前端调用容易误用路径 | 后续统一任务运行资源的 API 命名空间 |
| UI-08 | 研究数据上下文可能不完整 | 页面已展示版本、质量、来源等字段，但后端缺失时只能显示未返回 | 用户无法完整判断研究可信度 | 完善 DataContext 字段契约，不用页面默认值掩盖缺失 |

| UI-11 | 缓存版本号未完全统一 | 不同模板引用公共 CSS/JS 时版本号可能不同 | 浏览器可能短暂使用旧资源 | 每次公共资源变更统一更新版本号，最终改为构建哈希 |

## 19. 前端工程与数据一致性约束

本章是把全量审视发现的问题固化为**强制约定**。任何页面在前端改版或新增时都必须满足，作为实现和验收的硬性标准。

### 19.1 统一的页面状态词表

前端不得各自维护一套状态中文文案。所有状态必须在单一常量表中定义，页面统一引入：

| 状态值（后端） | 统一中文口径 | 颜色 | 语义 |
|---|---|---|---|
| `healthy` | 正常 | 绿 | 数据/结果可按当前口径使用 |
| `stale` | 待更新 | 橙 | 有结果但落后于预期 |
| `partial` / `partial_success` | 部分可用 | 橙 | 核心可用，部分能力缺失 |
| `critical` | 异常 | 红 | 最近失败或严重滞后 |
| `failed` | 失败 | 红 | 最近一次运行失败 |
| `running` | 运行中 | 蓝 | 任务或研究正在执行 |
| `deferred` | 延期 | 灰 | 设计存在但数据契约未完成 |
| `disabled` | 未启用 | 灰 | 调度未开启 |
| `empty` | 暂无数据 | 灰 | 没有实际数据，不可伪造为 0 |
| `not_applicable` | 不适用 | 灰 | 该证券类型不适用该项 |
| `unknown` | 状态未知 | 灰 | 无法判断 |

**约束**：
- 同一状态值在任何页面都显示同一中文和颜色；
- 禁止出现“待更新”和“有些滞后”并存、“异常”和“严重异常”并存的情况；
- 状态映射表集中在前端 `status.js`（或等价共享常量），页面级脚本只引用。
- 新增状态值时先更新词表，再开发页面，不允许页面自行添加文案。

### 19.2 统一的响应信封

所有 API 前端必须只解析一种响应格式。新业务接口和旧接口统一按以下信封返回：

```text
{"status": "success" | "error", "data": {...}, "error": "...", "request_id": "..."}
```

**约束**：
- 前端封装统一 `request(url, options)` 适配器，负责错误抛出，不在每个页面重复判断 `d.status === 'success'`；
- 不再混用「读 `d.data`」和「读 `d.status` 直接取字段」两套写法；
- 错误必须带可读 `error` 文本，允许前端直接展示，不返回裸异常栈。

**后台配合项**：旧接口部分返回 `{status, items}` 而新接口返回 `{status, data}`，需要在适配器内明确完成一次映射，并记录在字段映射表中。

### 19.3 数据新鲜度单一来源

“数据是否新鲜”只允许一个判断来源，前端不得在两套接口之间自行选择：

| 现状 | 问题 | 约定 |
|---|---|---|
| 工作台用 `/api/data/status` | 同一个 daily 可能在两页显示不同状态 | 统一使用 `overall_status/datasets/latest_value` 作为页面事实 |
| 数据中心用 `/api/data-center/overview` | 状态来源与字段口径不同 | 数据中心保留数据资产和任务，不重复计算新鲜度 |

**约束**：
- 工作台、数据中心、观察池、研究页判断数据滞后时，统一读取“数据健康”来源；
- 若临时必须读两种接口，适配层负责把两者归一为同一 `status/latestDate/expectedDate/message` 模型；
- 页面不自行用“自然日”推算滞后，不自行拼市场状态。

### 19.4 覆盖统计的口径

覆盖数必须区分“暂无数据”和“0 覆盖”，不得相互混淆：

| 场景 | 显示 |
|---|---|
| `/` 无覆盖统计 | 暂无覆盖数据 |
| 覆盖为 0 | 0 / 预期数（比例 0%） |
| 证券类型不适用 | 不适用 |
| 证券类型无统计 | 暂无类型覆盖数据 |

**约束**：页面 Adapter 统一用单一函数处理覆盖文案，禁止在多个页面各写一套 `covered || 0` 的默认值逻辑。

### 19.5 任务运行的可追踪性

任务执行和重试操作必须能映射到具体运行记录：

| 操作 | 约定 |
|---|---|
| 执行任务 | 页面应能展示本次提交对应的 `run_id` 或运行记录 |
| 重试 | 应展示被重试的 `run_id` |
| 运行中 | 展示状态、阶段、进度 |
| 完成/失败 | 展示最近结果或错误原因 |

**约束**：前端展示“已提交”必须同时给出可追踪标识；后台若暂未返回 `run_id`，适配层需明确标注“当前接口未返回运行编号”，不得伪装成已关联某次运行。

### 19.6 渲染逻辑单一来源

同一个数据项的详情渲染只能有一个实现：

| 现状 | 问题 | 约定 |
|---|---|---|
| `data-module.js` 与 `data-center-adapter.js` 各写一套资产详情渲染 | 改一处漏两处 | 数据资产详情渲染收敛到单一 Adapter |

**约束**：
- 删除无页面引用的旧脚本（如当前未引用的 `data-module.js` 逻辑）；
- 同一区域只存在一个负责内联 HTML 拼接的函数；
- 页面模板只做骨架，数据拼接一律在页面级 Adapter 中。

### 19.7 页面壳层与导航统一

当前系统存在“新深色侧栏工作区”和“旧 `app + _nav` 顶栏”两套壳层。约定如下：

| 页面类别 | 壳层 |
|---|---|
| 系统工作区（工作台、数据中心、任务中心、通知、诊断） | 统一深色侧栏工作区 |
| 业务页（市场、发现、观察、持仓、复盘、研究、设置） | 统一顶栏 + 一级/二级导航 |

**约束**：
- 同类页面必须使用同一壳层，不允许同一类别内一页侧栏一页顶栏；
- 是否全量迁移到侧栏由统一审视决定；在未决定前，至少保证页面类别内一致；
- 页面主菜单高亮项必须与当前路由匹配，避免用“静态 active”误导用户。

### 19.8 交互反馈规范

| 反馈类型 | 约定 |
|---|---|
| 提交与否 | 页面内状态条或抽屉内反馈 |
| 轻量写入 | 页面内成功/失败提示 |
| 风险确认 | 使用确认组件说明影响、范围和是否可逆 |
| 编辑取值 | 使用表单或面板，不使用 `prompt` |

**约束**：主要流程不使用浏览器原生 `alert`、`confirm`、`prompt` 作为最终反馈；危险操作确认框需说明影响对象和可恢复性。

### 19.9 动态选项来源

下拉筛选的选项必须来自接口或配置，不得写死：

| 现状 | 问题 | 约定 |
|---|---|---|
| 数据资产分类在模板写死 | 后端分类变化时筛选与数据不一致 | 分类/类型选项由接口返回，或由统一配置驱动 |

**约束**：筛选下拉的候选项不硬编码在模板；空选项、漏选项都要有兜底，避免“选不到已有项”。

### 19.10 研究页的可信数据上下文

研究详情页必须展示研究结论所依赖的数据版本、质量和滞后情况，让用户判断研究是否可信：

| 字段 | 约定 |
|---|---|
| `data_as_of` | 始终显示 |
| `dataset_version` | 有则显示，无则标注“未返回” |
| `quality_status` | 有则显示，无则显示“未返回” |
| `source` | 数据来源 |
| `fallback_used` | 是否使用降级/回退 |
| `is_stale` | 是否滞后 |

**约束**：研究页不得只显示“数据截至 X”；可展示的上下文字段必须齐全，缺失字段明确标注，不显示为空白或正常。

### 19.11 数值与展示口径

| 场景 | 约定 |
|---|---|
| 当前价不可用 | 显示“暂无价格”，不按 0 计算盈亏 |
| 方案状态未知 | 显示“未返回”或“未知”，不显示为空或默认发布 |
| 统计数据为空 | 显示“暂无复盘数据”，不渲染默认 0 |
| 同一对象多个口径 | 持仓数量等只允许一个接口来源，不在不同模块各算一遍 |

**约束**：数值缺失时优先明确标注；同一业务事实在同一页面只能有一个取值来源。
